Of course I showed her a couple beat-em-up style video games, and since my wife's a Marvel fan (hey, I am too, just not as much of one), we settled on Marvel Cosmic Invasion.

Thanks to the power of Fable 5, making a port shaped after JohnnyOnFlame's TMNT:SR was easy. Ok, ok, maybe not *that* easy. I mean, it ran. On my AYN Thor. But we all know that's not good enough. First, which depot do we use? MCI has a linux depot, so the natural inclination is to go with that. Except, the linux depot uses SDL3, and Windows uses SDL2. Problem solved. Next, what's the renderer? Vulkan. That's fine for higher power devices, but OpenGLES is the norm with ports and if I'm going to learn something, I need to *not* be satisfied here.

Before going further, it's worth explaining why a Windows game can run on an ARM64 handheld at all. MCI is a .NET game. `Game.exe` and `ParisEngine.dll` aren't x86 machine code, they're CIL bytecode, and bytecode doesn't care what CPU it lands on. Mono on the device runs the same bytes the game shipped with, and later AOT-compiles them to native ARM64 for speed. What can't run is the pile of native Windows DLLs sitting next to them: SDL2.dll, FNA3D.dll, FAudio.dll, fmod.dll are x86-64 through and through. So the launcher deletes those and the port supplies aarch64 builds of the same libraries, with a dllmap config redirecting every DllImport("SDL2.dll") to `libSDL2-2.0.so.0` without the game noticing. That swap only works because FNA was designed for it: it's the XNA reimplementation that deliberately sits on portable native libs. And where the game's behavior has to change, MonoMod patches the IL offline, no source code required. The files on the SD card are your own Steam copy; the port is scaffolding around them.

The first step was forcing FNA3D to use OpenGL + GLES3 instead of MCI's default Vulkan preference. The launchscript enforces this now, but the earliest wall was a black screen hang on every handheld I tested (AYN Thor, RG353V, RG40XXH). ParisEngine preloads assets on worker threads that create GL resources; FNA3D queues those to the main thread, but the main thread was gated behind `Present` *and* held locks the workers were waiting on. Classic standoff. Johnny's FNA3D patches for TMNT:SR were the right direction, but MCI differs in that the async split work was needed across both `ParisEngine.dll` and `Game.exe`.

Next, optimization. Johnny's TMNT patch compresses textures, and MCI is full of 4k textures (because the game was designed for modern consoles played on 4k displays). I took things a step further than TMNT and went with *R8 texture encoding* blended with *astc* for static textures. The encoding is classified off the animation data, where the patch can rely on the engine's real "is this indexed" flag and preserve palette swaps.

At this point, Cosmic Invasion was booting and looking good on my RG40XXH, but it wasn't smooth enough. It played okay for a while, but after some playtime the game locked up. Debugging found that the engine pre-creates one live FMOD instance across all four banks and never releases them. FMOD pins sample data while an instance exists, so the resident audio set only grows. The whole SFX bank ends up stuck in unevictable heap, which on weak hardware leads to thrashing and out-of-memory.

I attempted a patch which crashed at launch: `klass' not met`; turns out adding fields to the base sound class shifted `Game.exe` subclass's AOT field offsets. Oops, both assemblies (`ParisEngine.dll` and `Game.exe`) need to be AOT'd *together*. The real solution was to reclaim a non-music sound's FMOD instance after a tunable idle grace period and lazily recreate it on the next play. This bounds the resident set to whatever has been recently used, reducing memory by a large margin.

After MCI quit having crashes after extended playtime, it was time to buy back that sweet headroom that TMNT:SR has. Headroom is a bit of extra leeway to account for periodic spikes in CPU and memory during specific gameplay sequences. Without headroom, games can slow to a crawl as things take longer to process through the pipeline. To get headroom, I re-encoded the font atlases from R8 to astc 6x6 (same dimensions, no renderer change) which put headroom at around 140MB on the H700 (up from 45MB).

Now I have rocknix installed on all of my devices for multiple reasons: I enjoy rocknix, it gets OTA updates and fast bug fixes, I have more control as a power user, and I haven't kept up with other custom firmwares. I'm not bothered if it turns out my work isn't perfect everywhere, since accounting for every custom firmware under the sun is tantamount to a full time job I don't have time for. Instead, I rely on issues being reported to my github or to me directly on Discord. The day after I published MCI, I received a report of no audio on muOS. So for the first time in a while I flashed the cfw to a spare sd card to debug.

Cosmic Invasion uses FMOD for audio, diverging from TMNT:SR. FMOD picks its device by enumerating ALSA namehints. muOS routes `default` to PipeWire, but hides it from enumeration while PipeWire holds the codec exclusively; FMOD sees nothing playable. A fix was put in place for MCI on the port side, and the true solution belongs with muOS upstream.

Again, absolutely none of this would have been possible without JohnnyOnFlame's guidance and Fable 5. AI gives a project like this speed, but it takes a motivated individual with standards to drive it. AI can't replace human testing, for example. The AI brought the breadth I don't have, and I brought the hardware, the eyes and ears, the standards, and the judgement. The most useful thing you can ask when working with AI is, "are you sure?" The second most useful thing you can ask is "why?". Why does this work the way it does, why can't we do this, why, why, why. The more you learn about something you're unfamiliar with, the more confident you'll become when talking about it and collaborating with others. This is a life lesson that works whether or not AI is in the picture at all. AI, in the end, is a powerful tool that can teach you in whatever way you learn best.

In a way, I'm learning about using tools that my children will eventually use themselves; and I'll be able to teach them in ways that an AI can't. For now, though, my daughter doesn't care about ALSA namehints or texture encoding. She likes kicking butts, and now she can.
